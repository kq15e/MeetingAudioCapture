# インシデント対応ガイド

## 目的

録音不能、データ損失、権限問題などが発生したときに、利用者への影響を抑えつつ、調査、復旧、恒久対応を追跡可能にする。

## 重要度

| 重要度 | 基準 | 対応方針 |
| --- | --- | --- |
| S1 | 多くの環境で録音できない、または録音データを失う | 通常開発を止め、回避策と修正版を最優先する |
| S2 | 特定の環境で主要機能が使えない | 優先して調査し、次の修正版へ含める |
| S3 | 回避可能な不具合、軽微な表示・操作上の問題 | 通常のバックログとして扱う |

重要度は推測される技術的な難しさではなく、利用者への影響、範囲、回避策の有無で決める。新しい情報によって変更してよい。

## 初動

1. 不具合報告テンプレートでIssueを作成する。
2. 重要度、発生範囲、回避策の有無を記載する。
3. エラー全文、発生日時、アプリとmacOSのバージョン、録音モード、音声デバイスを確認する。
4. 音声本体、会議内容、個人情報、認証情報をIssueやログへ添付しない。
5. S1またはS2では、利用可能な回避策を調査完了前でもIssue冒頭へ記載する。

## 調査

事実、仮説、未確認事項を分けて記録する。

- 事実：エラー文、コード上の発生箇所、再現結果など。
- 仮説：環境変更、OS更新、特定デバイスへの依存など。
- 未確認事項：不足しているログ、試していない環境など。

調査用ブランチまたは修正ブランチは、最新の`main`から作成する。調査中のログ追加も本番へ残す価値があるか確認し、音声データそのものは保存しない。

## 修正と検証

1. 原因を再現する自動テストを可能な範囲で追加する。
2. 修正範囲を原因に限定する。
3. 既存のビルドとテストを実行する。
4. 関係する録音モードとデバイスで実機確認する。
5. PRに対象Issue、原因、修正方針、確認環境、リスク、戻し方を記載する。
6. CI成功後にレビューし、`main`へマージする。

緊急修正でも、原因と検証結果を記録せずに`main`へ直接変更しない。

## 終了条件

次を満たした時点でインシデントを終了する。

- 影響と根本原因が説明できる。
- 修正または合意した回避策が利用可能である。
- 対象環境で再現しないことを確認した。
- 回帰テストが追加され、CIが成功している。
- Issue、PR、必要な恒久ドキュメントが相互に関連付いている。

## 振り返り

S1と、再発したS2では、Issueまたは`docs/`に短い振り返りを残す。

- 何が起きたか
- なぜ検知や診断に時間がかかったか
- 何が被害を抑えたか
- 再発防止策と担当Issue

一時的な時系列や試行錯誤はIssueへ残し、今後も有効な設計制約、診断方法、復旧手順だけを`docs/`へ反映する。
